# SLOs, error budgets and burn-rate alerts: spec

Draft, 2026-10-30. Steps 1 to 4 are built (see state.md); the rest is not. It turns "SLOs as objects" (the
first gap picked from a comparison with what other monitoring products
show) into decisions precise enough to build from. Open questions are at
the end.

## What exists to build on

- Recording rules (`internal/rules`): `record:` in metric and log groups,
  written to the metric store by `Manager.record`.
- Rule groups generated by the server: `cost_rules.yaml` is added next to
  the rule file while `costs.tokens` has entries
  (`internal/server/integrations.go`). SLO rules are generated the same way.
- Indicators already measured:
  - probes: `probe_success` per probe, target and checking agent;
  - spans: `traces_spans_total` and `traces_span_duration_seconds_bucket`
    by service, span name, kind and status. Counted on the agent from every
    span **before** sampling, so they are complete even with
    `otlp.traces.sample` set. Buckets are fixed (`durationBuckets` in
    `internal/otlp/traces.go`: 5 ms … 30 s);
  - any exporter's counters: HAProxy, nginx and the like by status code.
- Incidents (`internal/incidents`) turn any firing alert into an incident
  with a timeline; the Home page shows them.
- The cost rules' lesson: count per minute with `increase(...[1m])` and add
  the minutes up with `sum_over_time`; `rate()` over long windows double-
  counted series that live a few minutes (pods, restarts).

## Terms

| Term | Meaning |
|---|---|
| SLI | a ratio of good events to all events, measured by vigil |
| objective | the share that has to be good, e.g. 99.9 % |
| window | the period the objective is judged over: 30 days rolling, or a calendar month |
| error budget | `1 − objective` of the window's events; 0.1 % at 99.9 % |
| burn rate | how fast the budget is spent: error ratio ÷ (1 − objective). 1 spends exactly the budget in one window |
| SLA report | what an SLO achieved over a closed calendar period, for people outside the team |

## The SLO object

```yaml
name: shop-api-availability        # [a-z0-9-], unique, stable: it is the label `slo`
service: shop-api                  # display and grouping; the `service` label on alerts
owner: team-shop                   # who is told; never a person's name in vigil's own files
description: Requests to the shop API answer without a server error.
objective: 99.9                    # percent, 50 < x < 100
window: 30d                        # 7d | 28d | 30d rolling (default 30d), or `calendar_month`
indicator:                         # exactly one of the kinds below
  span:
    service: shop-api
    kind: server                   # default server
    span_name: ["GET /cart", "POST /checkout"]   # optional; all of the service otherwise
    latency_below: 500ms           # optional: also slow counts as bad; must be a bucket bound
alerting:
  page: true                       # fast burn, severity critical (default true)
  ticket: true                     # slow burn, severity warning (default true)
  min_events: 100                  # per hour; below it no burn-rate alert (low traffic)
labels: {team: shop}               # copied onto the recorded series and alerts
```

### Indicator kinds

All of them compile into two per-minute counts, `good` and `total`. That is
the one representation everything below is built on.

1. **`probe`**: time-based availability from a check vigil runs already.
   `probe: {name: shop-home, agents: [edge-1, edge-2]}` (agents optional:
   all agents that run that probe). Good = successful checks in the
   minute, total = checks in the minute:
   `sum(sum_over_time(probe_success{probe="shop-home"}[1m]))` and
   `sum(count_over_time(probe_success{probe="shop-home"}[1m]))`.
   Several agents checking one target count together: one region's view of
   a failure counts as partly bad, which is what users there saw.
   Not built: `latency_below` for probes (good = success and faster than
   the bound, from `probe_duration_seconds`, counted per sample).
2. **`span`** (above): request-based from traces. Total = increase of
   `traces_spans_total` for the selection; bad = `status="error"`, plus,
   with `latency_below`, requests above the bound
   (`total − bucket{le=bound}`). A bound that is not one of the fixed
   buckets is refused on save with the nearest bounds named, not rounded.
3. **`ratio`**: any counters, for exporters and the user's own metrics,
   as series selectors (vigil adds `sum(increase(...[1m]))` itself):
   ```yaml
   ratio:
     good:  haproxy_backend_http_responses_total{proxy="shop", code!="5xx"}
     total: haproxy_backend_http_responses_total{proxy="shop"}
   ```
   Or `bad:` instead of `good:`. Checked on save against the store; no
   data in the last hour is a warning.
4. **Not in v1: logs.** A LogsQL recording rule could count good and total
   lines per minute (`stats count() as total, count() if (status:~"5..")
   as bad`), and HAProxy access logs would make a good indicator. But lines
   arrive late (spools, Docker log stalls), and a rule that counts the last
   minute at `now` misses them, with no correction afterwards. Needs a
   counted-with-delay rule (evaluate `[now−3m, now−2m]`, stamp the sample
   at its minute); a later step.

### Where SLOs are kept

- In SQLite, table `slos` (tenant-qualified from the start, as the
  Foundations require for new tables), with versions like profiles:
  compare, restore.
- Edited on an SLOs page (admins), through `/api/v1/slos`, and from git with
  `vigil apply -f DIR` reading `DIR/slos/*.yaml` (origin `files`,
  `-prune` as for profiles and queries).
- Integrations may ship SLO **templates** with parameters (e.g. the HAProxy
  integration: "backend X answers without 5xx"), offered on the SLOs page
  for each backend or probe that exists; not created by themselves.
- Not in the rule file: an SLO generates several rules that must stay
  consistent, and the rule file has no place for versions or ownership.

## What an SLO compiles into

One generated rule group per SLO, `slo:<name>`, shown under Alerts > Rules
as read-only (like `builtin`). It is an aligned group: each whole minute is
evaluated once, at its end, 90 s after it ended, and missed minutes (up to
30) are evaluated late; see decisions.md.

```yaml
- record: slo_good_per_minute     # labels: slo, service, owner, + labels
  expr: <good count over the last 1m>
- record: slo_total_per_minute
  expr: <total count over the last 1m>
```

Plus `slo_objective{slo}` (the ratio, 0.999) as a third recording rule
(`vector(0.999)`), so dashboards and alerts can join on it.

Everything else is `sum_over_time` over those two series, one series each
per SLO, so a 30-day window is cheap and immune to series churn:

- error ratio over W: `1 − sum_over_time(good[W]) / sum_over_time(total[W])`
- budget left: `1 − error_ratio(window) / (1 − objective)`; negative when
  spent
- burn rate over W: `error_ratio(W) / (1 − objective)`

**Gaps:** a minute the server did not evaluate (restart, store down) is
counted as neither good nor bad; up to 30 missed minutes are counted
late, from the counters still in the store. The SLO shows its **coverage**: minutes
recorded ÷ minutes in the window. Below 99 % the page says so next to the
number; an SLA report states it. Backfilling missed minutes from the
counters beyond those 30 minutes is a later step.

**A changed indicator** starts a new version: series carry
`slo_version`, the window shows where the version changed, and the budget
is computed across versions without mixing in silent rewrites of history.

## Alerts: multi-window, multi-burn-rate

The usual scheme (Google's SRE workbook), fixed in v1 and computed for the
SLO's window length (factors below are for 30 days):

| Alert | Severity | Burn rate | Long window | Short window | Spends |
|---|---|---|---|---|---|
| `SLOBurnFast` | critical | 14.4 | 1h | 5m | 2 % of the budget in an hour |
| `SLOBurnFast` | critical | 6 | 6h | 30m | 5 % in six hours |
| `SLOBurnSlow` | warning | 3 | 1d | 2h | 10 % in a day |
| `SLOBurnSlow` | warning | 1 | 3d | 6h | 10 % in three days |

- Both windows must burn faster than the rate: the long one shows it is
  real, the short one that it is still happening (so the alert resolves
  soon after the cause stops).
- As built (2026-10-31): the rate is `spend × window ÷ long window`, so
  other windows spend the same share. The alerts run in their own group
  `slo:<name>:alerts`, not aligned, and read the minutes with `offset 2m`
  (good and total of the newest minute are two writes; one was seen
  without the other, a page at 74.8 % for 7.7 %). A burn alert needs the
  SLO to have counted for ¾ of its long window, `SLOBudgetExhausted` for
  ¼ of the SLO's window (`tfirst_over_time`, MetricsQL): a new SLO paged
  off 8 checks right after it was created.
- `min_events`: no burn-rate alert while the long window holds fewer
  events than that per hour; one failed request of three is not a page.
  Probe SLOs have a known rate and skip it.
- `SLOBudgetExhausted` (warning) while budget left ≤ 0; rolling windows
  only (a calendar month's elapsed range cannot be written in a static
  rule).
- Labels: `slo`, `service`, `owner`, `severity`, the SLO's labels.
  Annotations: the burn rate, budget left, and a link to the SLO's page.
  `runbook_url` from the SLO if it has one.
- Incidents: kind `slo`, resource the SLO name. When the alert that causes
  the burn also fires (`ProbeFailing` for a probe SLO, HAProxy 5xx), the SLO
  incident is listed next to it, not merged: one is the cause, the other
  is how much it costs. A parent link by shared `service` label comes with
  the catalog.

## UI

- **SLOs page** (`#/slos`, in the menu once one exists): a row per SLO
  with objective, achieved over the window, budget left (bar), burn rate
  over 1h, coverage, open alerts. Filter by service, owner, label.
- **An SLO's page:** budget burn-down over the window (budget left per
  day, a straight line for "spent evenly"), error ratio and total events
  over time, the four burn rates now, incidents and silences in the
  window, version changes, the generated rules (read-only), and for `span`
  SLOs the worst operations in the last day (from the existing spans
  metrics). Deploy markers once DORA's change ledger exists.
- **Home page:** an SLO that alerts is an incident like any other; budget
  below 25 % with more than a week of the window left is a "coming" item
  next to the disk and certificate forecasts.
- **Dashboards:** no new panel type. A starter dashboard "SLOs" built from
  the recorded series and `slo_objective`, and a variable `slo`.

## SLA report

- For a closed calendar month or quarter: per SLO the objective, achieved
  share, met or missed, budget used, the minutes or requests that were bad,
  the worst day, coverage, and the incidents in the period with their
  duration and acknowledgement comment.
- On the SLO page and `GET /api/v1/slos/report?period=2026-10`, as JSON,
  CSV and a printable page. Computed from the recorded series at request
  time; a closed month's result is stored once, so a later change to the
  SLO or to the store's retention does not change a report already given.
- Not built: service credits, contract terms, customer names. vigil says
  what was measured; what a contract makes of it is not vigil's.
- Retention: a 30-day window and monthly reports need the recorded series
  for at least 35 days in the metric store (check the trial's retention
  setting). Stored monthly results outlive it.

## Regions and tenants

- SLO rules have authority `region` (see [regions.md](regions.md)); an SLO
  over several regions is defined at central as `sum` of the regions'
  `good` and `total` minutes, which central's "sum, count, min, max only"
  rule allows. Ratios must never be averaged across regions; counts make
  that impossible to get wrong.
- Every SLO, version and stored report belongs to a tenant.

## Build order

1. SLO object, table, validation against the store, `/api/v1/slos`,
   `vigil apply`; rule generation for `probe`, `span` and `ratio`;
   `slo_objective`; tests that the generated expressions give the expected
   ratios over a fixed series.
2. Burn-rate alerts, `min_events`, incidents of kind `slo`.
3. SLOs page and an SLO's page; Home page items; starter dashboard.
   Built 2026-10-31. For step 4: `GET /api/v1/slos/report` would be
   taken by `GET /api/v1/slos/{name}` for an SLO named `report`; refuse
   that name in `Check` (or put the report under a query parameter, as
   the status is: `?status=1`).
4. SLA report and stored monthly results. Built 2026-10-31 (quarters
   too); the names `report` and `reports` are refused for SLOs.
5. Integration templates (HAProxy, nginx, probes); `docs/slo.md`.
6. Later: logs indicator with delayed counting, backfill of missed
   minutes, error-budget policy (e.g. a rollout pauses itself while an SLO
   of the service burns fast), OpenSLO import.

Each step is checked on the Lima host with a probe pointed at a container
that is stopped and started, and with `vigil tracegen` for spans; the
burn-rate alerts with a replayed day of minutes rather than waiting.

## Decided

- Default window: 30 days rolling (owner, 2026-10-30). Calendar months
  stay available per SLO, and SLA reports are per calendar month whatever
  the window.
- Who sees what (owner, 2026-10-30): viewers see the SLOs page, an SLO's
  page and the reports; only admins create, change or delete SLOs. People
  without a vigil account get a report as an export (CSV or the printable
  page, saved as PDF by the browser); no public report links. A read-only
  token (`vgr_…`) can fetch `/api/v1/slos/report` like any other GET, for
  a system that collects reports itself.
- Error-budget policy (owner, 2026-10-30): after DORA, not in v1. Pausing a
  rollout because a service's budget burns needs to know which rollout
  touches which service, and that link comes with DORA's change ledger and
  catalog. v1 only shows the budget; it stops nothing.

No open questions left; the spec is ready to build from step 1.
